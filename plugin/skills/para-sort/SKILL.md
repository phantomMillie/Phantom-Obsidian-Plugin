# PARA 정리 — 판단은 지금 쓰고 있는 AI 가

스크립트는 줍고 · 보여 주고 · 쓰기만 한다. **기록할지 · 어디로 · 어떻게 쪼갤지는 네가 판단한다.** 키나 별도 LLM 호출은 없다.

```bash
P="python3 ${MILLIE_HOME:-$HOME/.millie-obsidian}/para"
$P/collect.py --no-llm            # 1. 지난 대화에서 끝난 일을 줍는다 (빠름, LLM 없음)
$P/classify.py --pending --claim  # 2. 정리할 목록 + 잠금. "대기 없음" · "다른 대화가 정리 중" 이면 거기서 끝
#                                   3. 아래 기준으로 판정 JSON 을 파일에 쓴다 (예: /tmp/para-verdict.json)
$P/classify.py --apply /tmp/para-verdict.json   # 4. 적용 — 마지막 줄을 그대로 한 줄 보고
```

판정 도중 멈추게 되면 `$P/classify.py --release` 로 잠금을 푼다(30분 지나면 저절로 풀린다).

## 판정 JSON

목록의 `[id]` 마다 하나. 목록에 없는 id 는 쓰지 않는다. 빠뜨린 id 는 인박스에 그대로 남는다.

```json
{"results": [
  {"id": "a1b2c3d4e5f6", "action": "skip", "reason": "상태 확인 질문"},
  {"id": "0f9e8d7c6b5a", "action": "defer", "reason": "수정 중 — 사용자 확인 전"},
  {"id": "1234567890ab", "action": "record", "items": [
    {"kind": "project", "target": "뷰어 개선", "section": "이슈",
     "line": "iOS 책 열기 크래시 수정 — 폰트 캐시 nil 강제 언래핑",
     "issue": {"section": "프로젝트 이슈", "line": "안드로이드 책 열기 크래시 — 재현 안 됨, 크래시 로그 필요"},
     "todos": [{"text": "안드로이드 크래시 로그 받아 원인 확인", "effort": "🔸"}]},
    {"kind": "area", "target": "보안 점검", "line": "..."},
    {"kind": "resource", "target": "정책", "line": "..."}
  ]}
]}
```

- `action`: `record` 기록 · `skip` 기록할 일 아님 · `defer` 아직 안 끝남(인박스에 남겨 다음에 다시 본다)
- `kind`: `project` · `area` · `resource`. `target` 은 목록에 있는 이름 **그대로** (프로젝트 · 영역 · 자료 주제)
- `section` (project): `한 일` 실제 작업 · `결정` 정한 것 · `이슈` 버그 · 막힘의 원인과 해결 · `외부` 다른 팀 · 외부 요청 · `로그` 그 밖
- `line`: 그곳에 남길 한 줄. 무엇을 했고 어떻게 끝났나. 120자 안쪽, 대화에 있는 말로만
- `issue` (project, 선택): **해결 안 된** 문제가 남았을 때만. `section` 은 `프로젝트 이슈` · `정책 이슈` · `일정 이슈`
- `todos` (project, 선택): 대화에서 **앞으로 하기로 한 일**만. `effort` 는 `⚡` 30분 · `🔸` 반나절 · `🧱` 하루 이상 (중요도 · 마감은 묻지 못하니 비운다)

## 기준

**기록하지 않는다 (`skip`)**
- 잡담 · 업무 외 · 말 다듬기 같은 일회성 부탁
- 상태 · 목록 확인, 조회, 설명만 듣고 끝난 질문 — 파일 · 설정 · 결정이 바뀐 게 없다
- `이미 기록` 에 같은 일이 있다 — 그 턴에 바로 기록했다. 거기 없는 다른 일만 기록한다
- 같은 대화를 여러 번 주웠고 뒤 기록에 이미 담긴 앞부분 — `reason` 에 "뒤 기록에 합침"

**아직 안 끝났다 (`defer`)**
- 고치는 중이고 사용자가 결과를 아직 확인하지 않았다 ("다시 확인해줄래?" 로 끝남, "아니 그거 말고" 뒤에 새 시도)
- 보류가 이미 붙어 있고 이번에도 끝이 안 보이면 계속 `defer`. 일주일 넘게 보류면 끝난 부분만 기록하거나 `skip`

**어디로 (`record`)**
- 판정 순서: 끝이 있는 일 → 프로젝트 / 지속 책임(정기 점검 · 운영) → 영역 / 나중에 찾아볼 지식 · 정리 → 자료
- 프로젝트 고르기: ① 대화 내용이 말하는 일 ② `폴더` 와 "코드 폴더 → 프로젝트" ③ `대화 프로젝트`(근거가 "프롬프트에 이름" 이면 이름이 지나가듯 나온 것일 수 있다 — 내용과 맞을 때만)
  - "결제 모듈 README 처럼 프로필 README 정리" 는 결제 일이 아니다. 고친 파일 · 폴더가 어느 프로젝트인지 본다
- **한 대화에 여러 일**이면 `items` 를 나눈다 — 프로젝트가 다르면 각 프로젝트로, 같은 프로젝트의 다른 일이면 항목을 따로
- 맞는 프로젝트가 없는 업무면 `미분류` 프로젝트. 새 영역 · 자료 주제가 맞으면 그 이름을 쓴다 — 바로 만들지 않고 사용자 승인 체크박스로 남는다
- 지어내지 않는다. 대화에 없는 원인 · 수치 · 다음 할 일을 만들지 않는다. **왜 그렇게 정했는지는 사용자가 이유를 말했을 때만** 적는다 — 비교표에 있던 장단점을 이유로 끌어오지 않는다
- 사용자가 "이건 X 프로젝트 일이야" 처럼 직접 말했으면 폴더 · 대화 프로젝트보다 그 말이 먼저다

## 보고

`--apply` 출력의 마지막 줄을 그대로 한 줄로: `PARA 정리 기록 N · 건너뜀 N · 보류 N · 승인 대기 N · 오류 N · 남은 대기 N`.
승인 대기가 있으면 "vault 루트 `📥 PARA 인박스.md` 에서 체크하면 다음 정리 때 만든다" 를 덧붙인다.
