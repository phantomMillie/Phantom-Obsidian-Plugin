# 팬텀 플로우 3~5단계 — 정책 QA 승격

경로는 `~/.millie-obsidian/config.json` 에서 읽는다 — `vault` 와 `paths`(vault 기준 상대 경로).
본문의 `<키>` = `<vault>/<paths.키>`. 설정에 없는 키는 사용자에게 묻는다.
`<vault>/AGENTS.md` 내용이 아직 컨텍스트에 없으면 먼저 읽는다.

완성 기준 하나: **QA가 이 문서만 보고 테스트할 수 있나.**
규칙 원본: `<method_doc>` 의 `🪜 5 단계` · `🏷️ 케이스 ID 명명 규칙` · `🚦 신호와 대응`.
완성형 예시: `<qa_example>` — 설정에 있을 때만 (구조만 참고, 링크 금지).

## 0. 전제

소스 플로우에 🧐 가 남아 있으면 **멈춘다.** 남은 목록을 보여주고 `flow-fill` 스킬로 돌린다.
일부 영역만 확정이면 그 영역만 승격할지 묻는다.

## 1. 용어 전환

- 노드 · 케이스는 사용자 조작 · 화면 · 정책 용어. 코드 심볼은 맨 아래 `🔗 소스 매핑` 표로만
- 낯선 용어는 `<glossary>` 확인. 없으면 `glossary-add` 후보로 보고에 적는다

## 2. 결정 테이블 (3단계)

- 진입 × 분기축 나열. 같은 동작이 여러 조합에서 반복되면 분류 코드(D1/D2/D3) + 카디널리티로 압축
- 케이스 ID는 원본 명명 규칙대로. 진입 문자가 새로 필요하면 사용자에게 확인

## 3. 단순화 (4단계)

동작이 같은 분류의 통합 **후보만** 제시한다. 합칠지는 사용자가 정한다.

## 4. 케이스마다 given

각 케이스에 "그 상태를 만드는 법"(계정 조건 · 데이터 · 설정 · 네트워크) 한 줄.
못 쓰면 테스트 불가 케이스 → `📌 미확정` 으로.

## 5. 자동화 매핑 (5단계)

- UI 테스트 함수를 grep으로 전수 → 케이스 ID와 1:1
- 매핑 안 되는 테스트나 케이스 = 누락 분기 신호. **임의로 보정하지 않고** 소스 플로우로 역추적한 결과를 보고

## 6. 쓰기

위치: 소스 플로우와 같은 폴더. 파일명 `✅ <프로젝트> <영역> QA.md`.
`<projects>/<이름>/` 이면 먼저 승인.

```yaml
---
type: qa
project: <프로젝트>
created: <오늘 YYYY-MM-DD>
tags: [qa, project/<프로젝트-공백은-하이픈>]
---
```

상단 네비: Overview · 소스 플로우 · 이슈. 소스 플로우 상단 네비에도 이 QA 링크 추가.

섹션 순서:
`🎯 QA 범위` → `🧭 큰 흐름` → `N️⃣ 진입별 (결정 테이블 · 케이스)` → `🧪 교차 확인 매트릭스` → `🧪 자동화 매핑` → `🔁 회귀 체크` → `📌 미확정 / 확인 필요` → `🔗 소스 매핑`

## 7. 완료 검사

- [ ] 모든 케이스에 ID + given
- [ ] 본문에 코드 심볼 없음 (소스 매핑 표 제외)
- [ ] 자동화 매핑 수치: 테스트 N · 케이스 M · 미매핑 목록
- [ ] 정책은 mermaid 흐름도, 표는 결정 테이블 · 매트릭스 · 매핑에만
- [ ] 프론트매터 `created` + `project/` 태그 · Store/Archives 링크 없음

`ai-check` 스킬이 있으면 결론 직전에 돌린다.
